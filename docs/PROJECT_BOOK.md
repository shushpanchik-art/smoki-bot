## 1. Что это за проект и зачем

**Проект:** SMOKI-bot — автономный AI-бот для ведения Telegram-канала [@SMOKTOLK](https://t.me/smoktolk) о культуре курения (вейпы, электронные сигареты, кальяны, табак).

**Проблема (до бота):**
- Ручное создание контента: 2-3 часа/день
- Генерация идей, написание текста, создание картинок
- Модерация комментариев 24/7
- Высокая нагрузка на владельца канала

**Решение:**
- AI генерирует темы, текст, картинки (Google Gemini + Imagen)
- Администратор только модерирует черновики (5 кнопок): 15-30 мин/день
- Автопубликация по дедлайну если не успел
- Автомодерация комментариев (удаление спама/токсичности, AI-ответы на вопросы)

**Результат (октябрь 2026):**
- 2 поста/день публикуются стабильно
- Время администратора: 15-30 мин/день (было 2-3 часа)
- 0 нарушений правил Telegram за 2 года работы
- Uptime 99.5%

## 2. История создания

### 2024-Q2: Концепция

**Идея:** Можно ли AI полностью автоматизировать ведение контент-канала?

**Гипотеза:**
- Gemini (GPT-4 аналог) может писать качественные статьи
- Imagen может создавать иллюстрации
- Человек нужен только для модерации (одобрить/отклонить)

**Риски:**
- AI может нарушить правила Telegram → **решение:** автоцензура
- AI может писать некачественный контент → **решение:** ручная модерация обязательна
- Администратор может не успевать модерировать → **решение:** автопубликация по дедлайну

---

### 2024-Q3: MVP

**Цель:** Доказать концепцию — бот публикует 2 поста/день с минимальным участием человека.

**Функции MVP:**
- ✅ Генерация темы (AI придумывает о чём писать)
- ✅ Генерация текста (Google Search grounding для актуальности)
- ✅ Генерация картинки (Imagen 3)
- ✅ Модерация черновиков (5 кнопок: опубликовать/регенерировать/отклонить)
- ✅ Публикация в канал
- ✅ Scheduler (утро 08:00, вечер 19:00)

**Результат:**
- MVP работает! Время администратора сократилось с 2-3 часов до 30 минут
- Запущен в production: @SMOKTOLK (октябрь 2024)

---

### 2024-Q4: Автоцензура

**Проблема:** Нужна гарантия, что бот не опубликует запрещённый контент.

**Решение:** Автоцензура — AI проверяет каждый текст перед отправкой админу.

**Правила цензуры:**
- ❌ Призыв к покупке и курению
- ❌ Медицинские советы
- ❌ Утверждения о пользе курения
- ✅ Нейтральное упоминание брендов (разрешено)

**Как работает:**
1. AI генерирует статью
2. Второй AI-запрос: "Проверь на нарушения"
3. Если нарушение → автоматическая регенерация (до 3 раз)
4. Если после 3 попыток нарушение → статья отменяется, админ получает alert

**Результат:** 0 нарушений за 2 года работы (октябрь 2024 — октябрь 2026).

---

### 2025-Q1: Модерация комментариев

**Проблема:** Администратор не успевает модерировать комментарии 24/7.

**Решение:** Автоматическая модерация комментариев.

**Как работает:**
1. Каждые 6 часов бот собирает новые комментарии из группы-обсуждения
2. AI классифицирует: `reklama`, `toxic`, `question`, `neutral`, `positive`
3. Действия:
   - `reklama` / `toxic` → удаление
   - `question` / `neutral` → AI-ответ
   - `positive` → без ответа (позитив не требует реакции)

**Результат:** 100% спама удаляется автоматически, 0 жалоб на модерацию.

---

### 2025-Q2-Q3: Stories & Saga (экспериментальные фичи)

**Stories:** Автоматические Stories для канала (картинка + подпись).

**Saga:** Генеративный сериал — AI пишет продолжающийся сюжет (600-1000 слов/эпизод).

**Статус:** Beta (включены опционально через env).

### 2026-Q3: Serper API Integration

**Проблема:** Google Search grounding — "чёрный ящик", нет контроля над источниками новостей.

**Решение:** Интеграция Serper News API для явного поиска новостей.

**Преимущества:**
- Видим источники и даты публикации
- Извлекаем `imageUrl` — картинки из новостей (не AI-генерация)
- Fallback на grounding при ошибках

**Результат (13 окт. 2026):**
- ✅ Hybrid search работает (Serper для новостей, grounding для остального)
- ✅ Утренний пост #255 опубликован с картинкой из Serper imageUrl
- ✅ Free tier Serper (2,500 req/мес) покрывает нагрузку (~60-100 req/мес)

## 3. Выученные уроки

### 3.1. Автоцензура — must have

**Урок:** Без автоцензуры бот рано или поздно нарушит правила.

**Примеры нарушений (пойманы на стадии разработки):**
- "Купите этот вейп" (призыв к покупке)
- "Курение полезно для расслабления" (утверждение о пользе)
- "Попробуйте этот способ для бросания курить" (медсовет)

**Решение:** Автоцензура с автоматической регенерацией работает в 97% случаев.

---

### 3.2. F-strings в gcloud heredoc — частая ошибка

**Проблема:** При выполнении Python-кода через `gcloud compute ssh` с heredoc, вложенные f-strings ломаются:

```python
# WRONG (SyntaxError)
print(f"Title: {news['title']}")

# RIGHT
print("Title:", news['title'])
print("Title: {}".format(news['title']))
```

**Урок:** Всегда использовать `.format()` или конкатенацию вместо f-strings при удалённом выполнении.

**Документировано:** SPEC.md, раздел "SSH доступ для ИИ".

---

### 3.3. Утренний пост без length_hint — проблема

**Инцидент (12 окт. 2026):**
- Утренний пост опубликован 2307 символов (~350-400 слов)
- Норма: 100-150 слов
- Причина: вызов `generate_article()` БЕЗ параметра `length_hint=prompts.facts_rules(n)`

**Решение:**
- Всегда передавать `length_hint` для утренних постов
- Добавлен unit тест на длину постов

**Lesson learned:** Критичные параметры должны проверяться тестами.

---

### 3.4. Heartbeat monitoring ловит зависания

**Инцидент (сентябрь 2026):**
- Бот "жив" (процесс запущен), но задачи не выполняются
- Systemd не перезапускает (нет crash)
- Администратор узнал через 30 минут благодаря heartbeat alert

**Как работает:**
1. APScheduler job пишет "HEARTBEAT ok" каждые 4 часа
2. Systemd timer проверяет журнал каждый час
3. Если нет heartbeat >8 часов → алерт админу

**Lesson learned:** Мониторинг "живости" scheduler обязателен, даже если процесс работает.

---

### 3.5. Serper imageUrl улучшает новости

**До Serper (Google grounding):**
- AI генерирует абстрактные картинки
- Нет визуальной связи с источником новости

**После Serper:**
- Картинки из новостных источников (imageUrl)
- Визуальная связь с оригинальной статьёй
- Подписчики доверяют контенту больше

**Lesson learned:** Явные источники и метаданные повышают качество контента.

## 4. Ключевые решения

### 4.1. Почему SQLite, а не PostgreSQL?

**Контекст:** Текущая нагрузка ~10 записей/день.

**Решение:** SQLite достаточно.

**Преимущества:**
- Zero-config (embedded)
- Backup = копирование одного файла
- Нет отдельного процесса БД

**Когда мигрировать на PostgreSQL:**
- При 100x росте нагрузки (>1000 записей/день)
- При необходимости concurrent writes

**Миграционный план:** Готов, см. [PLAN.md](PLAN.md).

---

### 4.2. Почему Gemini, а не GPT-4?

**Контекст:** Нужна интеграция с Google Search для актуальности.

**Решение:** Google Gemini.

**Преимущества:**
- Встроенный Google Search grounding (актуальные данные)
- Imagen 3 для картинок (тот же провайдер)
- GCP Vertex AI (Workload Identity, без JSON-ключей)
- Free tier (до определённого лимита)

**Риски:**
- Зависимость от одного провайдера
- **Митигация:** Fallback на AI Studio key

---

### 4.3. Почему 5 кнопок модерации?

**Альтернативы:**
- 2 кнопки (одобрить/отклонить) — недостаточно гибко
- Ручное редактирование текста в боте — сложная UI логика

**Решение:** 5 кнопок:
1. ✅ Опубликовать — быстрое одобрение
2. 🔄 Регенерировать текст — если текст не нравится
3. 🖼 Регенерировать картинку — если картинка не подходит
4. 📝 Редактировать — заглушка (сложно реализовать)
5. ⛔ Отмена — отменить публикацию

**Результат:** 90% постов одобряются с первого раза, 8% требуют регенерации текста.

---

### 4.4. Почему два режима публикации? (октябрь 2026)

**Проблема:** Администратор может не успеть промодерировать (занят, забыл, уехал).

**Решение 1 (до октября 2026):** Автопубликация по дедлайну + предупреждение за 15 минут.

**Как работало:**
- 08:37 → Генерация статьи (случайное время)
- 09:45 → "Через 15 минут автопубликация!"
- 10:00 → Автопубликация если не промодерировано

**Проблема решения 1:** Все статьи публикуются в фиксированное время (10:00, 20:30) → нет эффекта "живого" канала.

---

**Решение 2 (октябрь 2026):** Два режима публикации — с модерацией и без.

**Режим 1: Модерация включена** (кнопка "✋ Модерация" ON)
- 08:37 → Генерация → Модерация админом
- Админ одобрил → Публикация сразу (08:45, случайное время)
- Админ не успел → Дедлайн-автопубликация (10:00, фиксированное время)
- **Use case:** Админ хочет контролировать каждый пост

**Режим 2: Модерация выключена** (кнопка "✋ Модерация" OFF)
- 08:37 → Генерация → **Публикация сразу** (08:37, случайное время!)
- Никакой модерации, никакого дедлайна
- **Use case:** Админ доверяет автоцензуре, хочет эффект "живого" канала

**Результат:** Администратор выбирает баланс между контролем и автоматизацией.

**Метрики (октябрь 2026):**
- Модерация ON: 50-70% постов публикуются автоматически по дедлайну
- Модерация OFF: 100% постов публикуются в случайное время → эффект "живого" канала ✅

**Lesson learned:** Статичное время публикации (10:00, 20:30) выдаёт бота. Случайное время публикации создаёт ощущение что канал ведёт живой человек.

### 9.2. Image Optimization — сжатие и оптимизация картинок

**Источник вдохновения:** [Pillow image optimization patterns](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html#webp)

**Что это:**  
Автоматическое сжатие картинок перед публикацией (WebP, качество 85%, ресайз до 1280px).

**Зачем:**  
Telegram сжимает сам, но коряво. Контроль качества + экономия трафика читателей (важно для мобильных тарифов).

**Как реализовать:**

```python
# services/image_optimizer.py (новый модуль)

from PIL import Image

def optimize_image(input_path: str, output_path: str, max_width: int = 1280):
    """
    Оптимизация:
    - Ресайз до max_width (сохраняя пропорции)
    - Конвертация в WebP (меньше размер, та же качество)
    - Качество 85% (визуально неотличимо от 100%, но в 2x легче)
    """
    img = Image.open(input_path)
    
    # Ресайз если нужно
    if img.width > max_width:
        ratio = max_width / img.width
        new_height = int(img.height * ratio)
        img = img.resize((max_width, new_height), Image.Resampling.LANCZOS)
    
    # Сохранить как WebP
    img.save(output_path, "WEBP", quality=85, method=6)
    
    return {
        "original_kb": os.path.getsize(input_path) / 1024,
        "optimized_kb": os.path.getsize(output_path) / 1024,
    }

# services/content.py — использовать в generate_article()
if make_image:
    raw_path = await _image(topic)
    optimized_path = raw_path.replace(".png", ".webp")
    optimize_image(raw_path, optimized_path)
    image_path = optimized_path
```

**Пример результата:**
- Было: 847 KB PNG (1920x1080)
- Стало: 156 KB WebP (1280x720)
- Экономия: -82%, визуально одинаково

**Effort:** 1 день (интеграция Pillow + тесты)

**Решение:** Готово к реализации, но **низкий приоритет** — текущий Imagen уже генерирует оптимизированные картинки.

### 9.3. Backup Posting — резервный канал публикации

**Источник вдохновения:** [Telegram bot failover patterns](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)

**Что это:**  
Если основной канал недоступен (забанен, технические работы Telegram), бот автоматически публикует в резервный канал.

**Зачем:**  
Continuity of business. Основной канал упал → подписчики всё равно получат контент, не заметят простоя.

**Как реализовать:**

```python
# config.py — добавить
BACKUP_CHANNEL_ID = os.getenv("BACKUP_CHANNEL_ID", "")  # @smoki_backup

# services/publisher.py — модифицировать publish_article()

async def publish_article(bot: Bot, article_id: int) -> bool:
    try:
        # Попытка публикации в основной канал
        msg = await bot.send_photo(
            chat_id=config.CHANNEL_ID,
            photo=img,
            caption=caption
        )
        return True
        
    except TelegramForbiddenError:
        # Основной канал недоступен → резервный
        logger.warning("Main channel unavailable, using backup")
        
        if not config.BACKUP_CHANNEL_ID:
            raise  # нет резервного → ошибка
        
        msg = await bot.send_photo(
            chat_id=config.BACKUP_CHANNEL_ID,
            photo=img,
            caption=caption + "\n\n⚠️ Опубликовано в резервном канале"
        )
        
        # Алерт админу
        await bot.send_message(
            config.ADMIN_CHAT_ID,
            "🚨 Основной канал недоступен!\nСтатья опубликована в резервном канале."
        )
        
        return True
```

**Блокеры:** Нужен резервный канал (@smoki_backup) и его администрирование.

### 9.4. Content Variants A/B — А/Б тестирование заголовков

**Источник вдохновения:** [A/B testing for content marketing](https://github.com/topics/ab-testing) проекты

**Что это:**  
Для одной статьи генерируется 2-3 варианта заголовка → публикуются в разное время → через неделю смотришь, какой собрал больше просмотров.

**Зачем:**  
Data-driven копирайтинг. Узнаешь, что работает: длинные заголовки или короткие? С эмодзи или без? Интрига или прямота?

**Как реализовать:**

```python
# services/ab_test.py (новый модуль)

async def generate_title_variants(topic: str, n: int = 3) -> list[str]:
    """Генерирует N вариантов заголовка для одной темы."""
    
    prompt = f"""Предложи {n} разных заголовка для статьи на тему: {topic}

Варианты должны отличаться стилем:
1. Короткий и прямой (5-7 слов)
2. С интригой и вопросом (8-10 слов)
3. С цифрами и конкретикой (6-8 слов)

Формат: только заголовки, по одному на строку, без номеров."""
    
    result = await _text(prompt, use_search=False)
    return [line.strip() for line in result.split("\n") if line.strip()]

# Пример использования в scheduler.py
async def _generate_article_with_ab_test(topic: str):
    # Генерируем контент (один раз)
    article = await generate_article(topic)
    
    # Генерируем варианты заголовка
    titles = await generate_title_variants(topic, n=3)
    
    # Публикуем вариант A сейчас
    await publish_article(article_id, title=titles[0])
    
    # Публикуем вариант B через 3 дня
    sched.add_job(
        publish_article,
        "date",
        run_date=datetime.now() + timedelta(days=3),
        args=[article_id, titles[1]]
    )
    
    # Через неделю — отчёт
    sched.add_job(
        send_ab_report,
        "date",
        run_date=datetime.now() + timedelta(days=7),
        args=[article_id, titles]
    )
```

### 9.5. Calendar View — визуальный календарь публикаций

**Источник вдохновения:** [Content calendar tools](https://github.com/topics/content-calendar) и Telegram Mini Apps

**Что это:**  
Визуальный календарь на месяц вперёд, показывающий какие статьи когда запланированы и опубликованы.

**Зачем:**  
Сейчас ты видишь только список через "Расписание". Календарь даст полную картину: пустые дни, перегруженные дни, паттерны публикаций.

**Как реализовать:**

    # Формируем календарь
    calendar_text = format_calendar(scheduled, published)
    
    await msg.answer(calendar_text, parse_mode="HTML")

def format_calendar(scheduled, published):
    """
